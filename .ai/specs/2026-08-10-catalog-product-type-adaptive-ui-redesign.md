# Catalog Redesign — Product-Type-Adaptive UI (Figma CRM canvas 2102:1393)

## TLDR

Redesign the catalog module's backend UI to the new Figma designs: a product list with hero header + KPI strip, lifecycle status tabs (All/Active/Draft/Archived), a table/grid view toggle, richer columns (product cell with thumbnail and variant count, category, price, soft-optional WMS stock, status badge), and a product-type-adaptive quick-create modal (Service / Physical / Subscription). The designs confirm one catalog UI adapted per product type; this spec adds the minimal additive data foundation (a `lifecycle_state` column, two new product types, list-decoration additions, a stats endpoint) and phases the remaining design surface (product card redesign, variant routes, price drawer, SaaS entitlements, PIM suite) into follow-ups. No existing contract surface is broken; every change is additive per `BACKWARD_COMPATIBILITY.md`.

## Problem Statement

The current products list is a plain DataTable (title/sku/type/flags/price/offers columns) and product creation is a heavyweight multi-step page. The new designs define a materially better catalog UX — status-tabbed browsing, at-a-glance KPIs, card-grid merchandising view, and one-step type-adaptive product creation — and establish the visual language for the whole catalog surface. The designs also assume concepts the data model lacks (product lifecycle draft/archived, service/subscription product types), which must be introduced additively.

## Proposed Solution

Keep every existing catalog contract (API shapes, ACL features, events, command ids, widget spots, search config) and layer the redesign on top:

1. **Data foundation (additive)** — `lifecycle_state` column; `service`/`subscription` product types; `variants_count` + `lifecycle_state` in the products list decoration; `lifecycleState` list filter; `GET /api/catalog/products/stats` for tab counts + KPIs.
2. **List page redesign** — new components in the catalog module (own-module pages are built directly, not via UMES): `ProductsHero` (title/subtitle + actions + KPI strip on `KpiCard`), lifecycle `Tabs`, restyled DataTable columns, `ProductsGridView` (client-side card grid over the same data), Table|Grid `SegmentedControl` toggle persisted per browser (localStorage, user-scoped key), all wired into the existing `ProductsDataTable` host so DataTable extension spots (`data-table:catalog.products*`), perspectives, exports, bulk actions and the merchandising-assistant trigger keep working unchanged.
3. **Quick-create modal** — `ProductQuickCreateDialog` on the list page: type segmented control (Service/Physical/Subscription), type-adaptive fields, submits ONE `createCrud('catalog/products', …)` call; the optional base price travels inside the create payload (`basePrice` sub-object) and is materialized server-side by the `catalog.products.create` command — atomic with the product, no client-side price-kind lookup, no compensation path. The full create wizard page remains for advanced creation ("Advanced editor" link in the modal footer).

Alternatives considered: repurposing `status_entry_id` for lifecycle (rejected — silent semantic change for existing API users); a separate `catalog_plans` module for subscriptions now (rejected — Phase-5 scope, needs entitlement data model); building the grid as a separate page (rejected — design shows a view toggle on one page; one host preserves table state and spots).

## Architecture

- All new UI lives in `packages/core/src/modules/catalog/components/products/` (components) and the existing `backend/catalog/products/page.tsx` host. No new module, no UMES for own pages.
- `commercialKind(productType): 'physical' | 'service' | 'subscription'` + `deriveProductDisplayStatus(row): StatusMap key` live in a new pure lib `packages/core/src/modules/catalog/lib/productPresentation.ts` (unit-testable, shared by table/grid/modal/detail phases).
- Stats endpoint `api/products/stats/route.ts` (hand-written GET, pattern of `api/settings/route.ts`): auth via `catalog.products.view`, tenant/org-scoped counts in ≤3 grouped queries (no per-row work; the lifecycle scope index covers them). Response `{ totals: { all, active, draft, archived }, productsInActiveOffers: number }`. **`totals.active` is the Active-TAB count — `lifecycle_state='active' AND is_active=true`** — so the tab pill, the Active KPI, and the tab's row set always agree; `totals.all/draft/archived` key on lifecycle alone. Deliberately uncached (the count queries are cheap; the existing `afterList` cost dwarfs them — see issue #2913, untouched). Org scoping uses the exact same scope-resolution path as the products list route, so pills and rows are computed over the same population; when the user applies ADDITIONAL filters (search, category, type) the pills intentionally keep showing per-lifecycle totals, not filtered counts (standard tab-badge behavior). Response casing: camelCase (a new hand-written endpoint, matching the categories/offers convention for hand-written responses).
- List decoration: `decorateProductsAfterList` additionally returns `variants_count` (single `COUNT … GROUP BY product_id` query over non-deleted variants, restricted to the page's product ids and the request's tenant/org scope) and `lifecycle_state` (already on the row; added to `list.fields`). Both additive keys — existing consumers (AI tools, WMS enrichers) are unaffected.
- STOCK column: a small **WMS-owned** DataTable injection column widget (`packages/core/src/modules/wms/widgets/injection/catalog-products-stock/`) targeting `data-table:catalog.products:columns` with widget features `['wms.view']`; it renders its own enricher's `_wms` row data (severity text + bar via status tokens). Catalog ships no `_wms` knowledge; the spot id already exists on the products table host.
- Stats-route dispatch: `api/products/stats/route.ts` is a static nested path; the products CRUD route lives at `api/products/route.ts` with no dynamic `[id]` segment (record lookup is a query param), so `/api/catalog/products/stats` cannot be shadowed. Covered by an integration test.
- The design's app chrome (sidebar/topbar) is NOT implemented — pages render in the existing backend layout.

## Data Model

Additive migration on `catalog_products` (single migration file + catalog module snapshot update via `yarn db:generate`):

```sql
ALTER TABLE catalog_products ADD COLUMN lifecycle_state text NOT NULL DEFAULT 'active'
  CONSTRAINT catalog_products_lifecycle_state_check CHECK (lifecycle_state IN ('draft','active','archived'));
CREATE INDEX catalog_products_lifecycle_scope_idx ON catalog_products (organization_id, tenant_id, lifecycle_state);
```

- Entity: `CatalogProduct.lifecycleState` (`text`, default `'active'`, `@Check` mirroring the SQL constraint); value set `CATALOG_PRODUCT_LIFECYCLE_STATES = ['draft','active','archived'] as const` in `data/types.ts`.
- Enum extension: `CATALOG_PRODUCT_TYPES` gains `'service'`, `'subscription'` (additive; `CATALOG_CONFIGURABLE_PRODUCT_TYPES` / `CATALOG_SUBPRODUCT_PRODUCT_TYPES` unchanged — services may still be configurable via the existing `is_configurable` flag). Reach note: the advanced create wizard and product edit page type selects source this list, so both automatically gain the two new options (new `catalog.products.types.service|subscription` i18n keys); wizard behavior for the new types is otherwise unchanged and it keeps creating `lifecycle_state='active'` products (server default — the wizard gains no draft support in this phase).
- Validators (`data/validators.ts`): `lifecycleState: z.enum(CATALOG_PRODUCT_LIFECYCLE_STATES).optional()` on create/update schemas (defaulted to `'active'` in create mapping only when absent — `.partial()` gotcha from the JJIT research respected: no `.default()` on the update schema). Create mapping defaults `requiresShipping=false` ONLY for the new `service|subscription` types when the field is not explicitly provided (pre-existing types, including virtual/downloadable, keep today's default).
- No other entity changes. `CatalogProductPrice`, offers, variants, categories untouched.

## API Contracts

All changes additive; response casing conventions per route are preserved (products stay snake_case).

1. `GET /api/catalog/products` — new optional query param `lifecycleState` (`draft|active|archived`); new response keys per item: `lifecycle_state`, `variants_count`. `productListItemSchema` and the OpenAPI query schema extended accordingly. The tab UI composes `lifecycleState` with the existing `isActive` param (Active tab sends both); the params stay independent at the API level.
2. `POST/PUT /api/catalog/products` — accept optional `lifecycleState`; `catalog.products.create/update` commands persist it (undo captures previous value like every other field).
2a. `POST /api/catalog/products` — new optional `basePrice: { unitPriceNet: string|number, currencyCode: string, taxRate?: number }` sub-object on `productCreateSchema` (`currencyCode` reuses the exact `currencyCodeSchema` the prices route validates with; `unit_price_net` is authoritative; because the write rides the shared `catalog.prices.create` path, `unit_price_gross` is derived exactly as a standalone price create would derive it (from `taxRate` when present), and display continues through the existing resolved-pricing render). **Server-side permission boundary:** a create request carrying `basePrice` additionally requires `catalog.pricing.manage` — enforced in the route's create path (not only in the UI); without the feature the request fails 403 before any write, keeping parity with the prices route's write gate. The `catalog.products.create` command resolves the tenant's `regular` price kind by code (same lookup `inbox-actions.ts` already uses, `inbox-actions.ts:72-81`) and creates a product-level `CatalogProductPrice` in the same command execution — atomic with the product and its `categoryIds`/`tags` assignments, and removed by the command's undo. **Side-effect parity:** the embedded price write goes through the same internal creation path `catalog.prices.create` uses (shared helper), so the `catalog.price.created` event and the price query-index event fire exactly as they would for a standalone price create. Create response gains additive `basePriceApplied: boolean`; when the tenant has no `regular` price kind the product is still created and `basePriceApplied` is `false` (the dialog flashes an informational message; multiple `regular`-coded kinds cannot exist — the code is unique per tenant). Validation errors in `basePrice` fail the whole create (no orphan product). `taxRate` absent → stored null (no default; the pricing render already handles null tax). An inactive or soft-deleted `regular` price kind counts as missing (`basePriceApplied:false`). Because the write goes through the shared `catalog.prices.create` creation path at the COMMAND layer, it carries the same undo capture, event emission, and query-index side effects as a standalone price create; route-level interceptors of the prices ROUTE do not run (the request enters via the products route) — command-level parity is the contract. SKU note: `sku` stays optional exactly as in the existing create schema; a duplicate SKU fails with the existing uniqueness error surfaced on the field. `handle` stays unset in quick-create (nullable column; editable later on the product page).
3. `GET /api/catalog/products/stats` — NEW (hand-written, `catalog.products.view`, tenant+org scoped, `withDeleted` never): `{ totals: { all: number, active: number, draft: number, archived: number }, productsInActiveOffers: number }`. OpenAPI doc exported like `api/settings/route.ts`. `all` = non-deleted total; **`active` = `lifecycle_state='active' AND is_active=true`** (matches the Active tab's compound filter exactly); `draft`/`archived` key on `lifecycle_state` alone; `productsInActiveOffers` = distinct products having an active, non-deleted offer.
4. No changes to offers/prices/categories/tags/price-kinds/option-schemas/settings/bulk-delete routes, events, command ids, ACL features, widget spot ids, search config, or DI keys.

## Edge Cases & Failure Scenarios

- Stats endpoint failure → KPI cards render error state; tabs render without counts (labels only); list unaffected.
- WMS absent / `wms.view` missing / enricher timeout (2s fallback) → the WMS column widget never mounts or renders empty for affected rows; catalog table unaffected.
- Quick-create with `basePrice` and no tenant `regular` price kind → product created, `basePriceApplied:false`, informational flash. Invalid `basePrice` → 400, nothing persisted (atomicity integration-tested).
- Draft products with no price/variants → list renders dashes; existing detail page unaffected (lifecycle field added to edit form in Phase 3; until then drafts are editable through the normal edit page which preserves unknown fields via passthrough).
- Tenant with legacy rows: all default `active` — tabs correct on day one. Migration index is a plain `CREATE INDEX` matching every existing catalog migration (no `CONCURRENTLY`; consistent with the module's migration style and current install sizes).
- `lifecycleState` invalid value in API → zod 400 (never persisted).
- `basePrice` without `catalog.pricing.manage` → 403 before any write (server-enforced; integration-tested).
- Variant-less quick-created products behave exactly like today's products created without variants via the API: product-level prices resolve through the existing pricing pipeline; nothing new constrains them.
- Existing Playwright specs (TC-CAT-001..035 etc.) rely on the current list markup — the redesign keeps DataTable semantics (role-based locators, search, filters) but specs asserting removed columns (`product_type`, `is_configurable` cells) or the old create-button navigation are updated in the same change (integration-coverage section below).

## Risks & Impact Review

- Blast radius: catalog list page + create-entry flow; products API additive keys; one migration. The de-facto `decorateProductsAfterList` contract only gains keys.
- Perspectives/saved views referencing the removed legacy column ids (`product_type`, `is_configurable`, `is_active`) degrade gracefully — unknown ids are ignored by the table state; the removed `status` filter id likewise (pinned by a component test).
- Rollback: migration is additive (column with default) — safe to leave in place if UI is reverted; UI changes are a single-page revert.
- Performance: one extra grouped COUNT per list load (variants_count) + one stats call per page mount; the known offers-decoration cost (#2913) is unchanged.
- Compatibility: no FROZEN surface touched (spot ids, event ids, command ids, ACL, routes all stable; enum + optional fields additive per BACKWARD_COMPATIBILITY.md).
